# BookBarcode 개발설계 — 바코드 판독 파이프라인 (Rev1 · 2026-09-05)

> 대상 독자: 이 저장소를 이어받는 개발자.
> 범위: 카메라 프레임이 ISBN 한 줄이 되기까지의 구조와 그렇게 만든 이유.

---

## 1. 왜 다시 설계했나

기존 구현은 `zbar-wasm` 한 엔진에 프레임 전체를 그대로 넘기는 단순 구조였다.
실사용에서 다음이 재현됐다.

- 바코드를 화면 가까이 대야만 읽힌다
- 조금만 흐리면 못 읽는다
- 기울여 찍으면 못 읽는다
- 같은 책을 계속 비추면 여러 번 기록된다

앞의 셋은 **판독 성공률** 문제이고 마지막 하나는 **기록 규칙** 문제다. 서로 다른 축이라 따로 다룬다.

## 2. 구조 한눈에

```
카메라 영상(video)
   │
   ├─ [빠른 경로] 변형이 필요 없는 전략 + 영상을 직접 읽는 엔진
   │       └─ 픽셀 복사 없이 engine.detectVideo(video)
   │
   └─ [일반 경로] 프레임 준비기(createFramePreparer)
           크롭 → 회전 → 리샘플 → 그레이스케일 → 명암 스트레치 → 언샤프
                                   │
                                   ▼
                          engine.detectBuffer(gray)
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                          ▼
        판독 성공                                    판독 실패
   PresenceGate 로 중복 억제                  ScanCycle 이 다음 조합으로
   → onDetect(isbn)                          (전략 → 없으면 다음 엔진)
              │
              ▼
   마커 오버레이 + 기록 API
```

핵심 파일

| 파일 | 역할 |
|---|---|
| `lib/scanner/pipeline.ts` | 순수 함수·순수 클래스. 전략 표, 명암 보정, 좌표 역변환, 멱등 게이트, 순환기 |
| `lib/scanner/frame.ts` | 캔버스로 프레임 한 장을 전략대로 다듬는다 |
| `lib/scanner/engines.ts` | 판독 엔진 세 종의 공통 계약과 지연 로드 |
| `lib/scanner/synth.ts` | 합성 바코드 장면 생성기(검증 전용, 제품 경로 아님) |
| `components/Scanner.tsx` | 카메라 제어, 스캔 루프, 마커 오버레이 |

## 3. 두 개의 사다리

### 3.1 엔진 사다리 (`engines.ts`)

| 순위 | 엔진 | 특징 | 없을 때 |
|---|---|---|---|
| 1 | 내장 `BarcodeDetector` | 영상 직접 판독, 픽셀 복사 0. 기울기·흐림에 가장 강함 | iOS 사파리엔 아예 없음 |
| 2 | `zxing-wasm` | `tryHarder`·`tryRotate`·`tryInvert` | — |
| 3 | `zbar-wasm` | 반듯하고 선명한 바코드에 빠름 | — |

**설계 근거는 측정이다.** 안드로이드 크롬 실기기, 합성 32케이스:

| 엔진 | 인식 |
|---|---|
| 내장 | 24/32 |
| zbar | 17/32 |
| zxing | 16/32 |

Node 벤치(2560×1440)에서는 **zxing 단독이 개편 전보다 낮았지만**(24 vs 25),
기울고 흐린 케이스를 zbar 가 놓친 자리에서 잡았다. 반대 방향도 있었다.
→ 어느 하나로 교체하는 것이 아니라 **놓치면 다음이 받는 구조**가 정답.

**지연 로드.** 엔진 자리(`EngineSlot`)는 미리 세우되 실제 로드는 순환이 그 자리에 처음 닿을 때 한다.
내장 엔진으로 다 되는 기기는 wasm 을 한 바이트도 받지 않는다.

**내장 엔진 채택 조건.** `getSupportedFormats()` 결과에 `ean_13` 이 **명시적으로** 있을 때만 쓴다.
안드로이드에서 Play 서비스 판독 모듈이 없으면 생성자는 성공하는데 목록이 비고
`detect` 가 늘 빈 배열을 준다. 조용히 아무것도 못 읽는 엔진이 맨 앞에 서는 것이 최악이다.

### 3.2 전략 사다리 (`pipeline.ts` 의 `SCAN_VARIANTS`)

| # | 이름 | 크롭 | 목표폭 | 보정 | 회전 | 노리는 상황 |
|---|---|---|---|---|---|---|
| 0 | `wide` | 전체 | 1280 | — | 0° | 가까이 댄 큰 바코드(가장 흔함, 가장 쌈) |
| 1 | `wide-boost` | 전체 | 1440 | 명암 | 0° | 조명이 나쁨 |
| 2 | `tele` | 62%×42% | 1680 | 명암 | 0° | 멀어서 작게 잡힘 |
| 3 | `wide-45` | 94% | 1440 | 명암 | 45° | 비스듬히 놓임 |
| 4 | `tele-sharp` | 62%×42% | 2000 | 명암+샤프 | 0° | 멀고 초점도 나감 |
| 5 | `tele-45` | 70%×62% | 1700 | 명암+샤프 | 45° | 멀고 기울어짐(가장 어려움) |
| 6 | `mid-sharp` | 86%×62% | 1800 | 명암+샤프 | 0° | 살짝 벗어난 위치 |

**왜 45°가 한 장이면 되나.** zbar 는 가로·세로 스캔라인만 쓴다.
0°와 90° 부근은 잘 읽고 그 사이(대략 25°~65°)가 사각지대다.
영상을 45° 돌리면 그 구간이 0° 부근으로 옮겨오고, 반대 대각선은 90° 부근으로 옮겨온다.
가로·세로를 모두 보는 한 **−45° 판은 중복**이라 넣지 않았다.

**순환과 고정.** `ScanCycle` 이 (엔진, 전략) 조합을 하나씩 돌린다.
성공하면 그 조합을 고정해 반복 인식을 빠르게 하고, 연속으로 6회 놓치면 상황이 바뀐 것으로 보고 탐색으로 돌아간다.

## 4. 전처리 — 무엇을 왜 하는가

### 4.1 그레이스케일

RGBA → 8bit 휘도(BT.601). `scanGrayBuffer` 로 넘기면 zbar 내부의 JS 변환 루프를 건너뛴다(속도).

### 4.2 명암 스트레치 (`buildStretchLut`)

흐리거나 역광인 프레임은 히스토그램이 좁은 구간에 몰려 이진화가 바 경계를 못 잡는다.
양 끝 1%를 잘라내고 남은 구간을 0..255로 편다.

**일부러 보정하지 않는 두 경우** — 값역에 「하지 않음(null)」이 있다.

- 폭이 220 이상: 이미 충분히 넓다. 건드릴 이유가 없다.
- 폭이 12 미만: 거의 단색이다. 펴면 **잡음만 증폭된다.**

### 4.3 언샤프 마스크 (`unsharpMask`)

`gray + amount × (gray − blur)`. 분리형 박스 블러(누적합)로 저주파를 얻는다.
초점이 나간 프레임의 바 경계를 되살리지만 비싸므로 사다리 뒤쪽 전략에서만 쓴다.

### 4.4 회전 시 두 가지 함정

1. **빈 모서리는 흰색으로 채운다.** 검은 여백은 굵은 바로 오인돼 판독을 망친다.
2. **그 흰 여백을 명암 표본에서 뺀다.** 여백까지 세면 분포가 밝은 쪽으로 쏠려
   「이미 충분히 넓다」로 판정돼 보정이 꺼진다. 여백이 닿지 않는 중앙 정사각형만 표본으로 삼는다
   (`buildStretchLut` 의 `sample` 인자).

## 5. 기록 규칙 — 멱등 (`PresenceGate`)

**규칙: 보이는 동안 1회.**

- 코드가 처음 보이면 기록한다.
- 계속 보이는 동안에는 무시한다.
- 1.5초 동안 한 번도 안 잡히면 「사라졌다」로 보고, 다시 나타나면 새 스캔으로 친다.

책을 뗐다 다시 대면 카운트가 올라가는 기존 기능(`scan_count`)은 그대로 유지된다.

> 이전 구현은 500ms 디바운스였다. 계속 대고 있으면 초당 2건씩 쌓였다.
> 디바운스는 「연속 프레임 노이즈」를 묶는 장치이지 「같은 대상」을 묶는 장치가 아니다.

`absenceMs = 1500` 을 고른 이유: 전략을 순환하는 동안 특정 바코드는 매 틱이 아니라
그 바코드를 잡는 전략이 돌아올 때만 검출된다. 순환 주기보다 넉넉해야 「사라졌다」로 오판하지 않는다.

## 6. 좌표 — 마커를 제자리에 찍기

판독 결과 좌표는 **스캔 버퍼** 좌표계다. 화면에 그리려면 원본 프레임 좌표로 되돌려야 한다.

`bufferPointToFrame(px, py, roi, scale, rotateDeg, bw, bh)`

- 회전이 없으면: `roi.x + px / scale`
- 회전이 있으면: 버퍼 중심 기준으로 옮긴 뒤 반대 방향으로 회전하고, 배율을 되돌려 ROI 중심에 더한다

그리고 **화면 좌표와 영상 좌표가 1:1 이어야 한다.**
컨테이너 `aspect-ratio` 를 실제 촬영 비율로 런타임에 맞추고 `object-fit: contain` 을 쓴다.
(기존에는 4/3 컨테이너에 `cover` 라 좌우가 잘려 보였고, 보이는 것과 스캔하는 것이 달랐다.)

## 7. 속도

| 수단 | 효과 |
|---|---|
| 내장 엔진에 영상 직접 전달 | 캔버스 그리기·`getImageData`·그레이 변환을 전부 건너뜀 |
| EAN-13 만 활성화 | zbar 가 다른 심볼 종류를 시도하지 않음 |
| `scanGrayBuffer` | zbar 내부 RGBA→gray JS 루프 회피 |
| 성공 전략 고정 | 연속 인식 시 사다리를 다시 돌지 않음 |
| 적응형 스로틀 | 직전 스캔 소요의 절반(30~200ms)으로 다음 시도 간격 조절 |
| 버퍼 재사용 | 매 프레임 수 MB 할당 → GC 끊김 방지 |

## 8. 검증 전략

| 층 | 도구 | 무엇을 잡나 |
|---|---|---|
| 단위 | `npm test` (node --test) | 멱등 게이트, 순환기, 좌표 역변환, 명암 보정 값역 |
| 회귀 벤치 | `npm run bench:scan` | 개편 전 대비 인식률. **회귀면 종료코드 1** |
| 실기기 | `/scan-lab` | 브라우저 내장 엔진 — Node 로는 **잴 수 없는** 유일한 경로 |

**합성 장면은 실제와 닮아야 뜻이 있다.** 처음 만든 장면은 원근·반사광·조명 기울기가 없어
개편 전 코드가 45° 기울기에서도 78%를 통과했다. 사용자가 보고한 증상과 맞지 않았다.
평면을 3D 로 기울여 **원근 왜곡**을 만들고 **반사광**과 **조명 기울기**를 넣은 뒤에야
실패가 사용자 증상과 같은 자리(멀고 흐린 케이스)에 몰렸다.

**남은 한계.** 실패 5건은 전부 거리 12~18% 에 흐림·반사광이 겹친 경우다.
초점 흐림은 각도 기준이라 해상도를 올리면 blur 도 같은 비율로 커진다.
**픽셀을 늘려서 풀리지 않는다.** 확대(zoom)·조명(torch)으로 물리적으로 푸는 것이 맞고,
두 제어를 화면에 노출해 두었다.

## 9. 이어받는 사람에게

1. `db push` 를 처음 돌릴 때는 **반드시 `--dry-run` 을 먼저 본다.**
   `0001_init.sql` 은 `drop table` 로 시작한다. 원격 이력이 비어 있으면 그것부터 실행된다.
2. 전략을 추가하면 `npm run bench:scan` 을 돌려 회귀가 아닌지 확인한다.
3. 엔진을 추가하면 `engines.ts` 의 슬롯에 넣고 구독할 전략 이름을 적는다.
   없는 이름을 적으면 `variantIndex` 가 **조용히 넘어가지 않고 멈춘다.**
4. 「이 폰에서 왜 안 읽히나」는 `/scan-lab` 을 그 폰에서 열어 답한다.
