# BookBarcode 개발설계 — 판매(POS) 시스템 (Rev1 · 2026-09-05)

> **설계만 한 문서다. 구현하지 않았다.**
> 착수 전에 이 문서로 범위를 합의한다. 특히 §7 의 미결 항목은 답이 나와야 짤 수 있다.

---

## 1. 무엇을 만드는가

바코드를 찍어 담고, 수량과 금액을 맞추고, 결제 수단을 골라 **판매를 확정**하는 화면.
포스기와 같은 흐름이되 이 앱의 재고와 이어져 있어야 한다.

**한 줄 요건** — 판매가 확정되면 재고가 그만큼 줄고, 그 사실이 되짚어진다.

### 범위 안

- 장바구니에 담기(바코드 스캔·목록에서 선택·수동 추가)
- 수량·단가 조정, 품목별 할인, 전체 할인
- 결제 수단 기록(현금·카드·계좌이체·기타) — **실제 결제 처리는 하지 않는다**
- 판매 확정 → 재고 차감 → 영수 내역 저장
- 판매 취소·부분 반품
- 일자별 매출 집계, 엑셀 내보내기

### 범위 밖 (이번에 안 한다)

- 카드 단말기·PG 연동, 현금영수증·세금계산서 발행
- 고객 관리, 적립·쿠폰
- 다중 매장·다중 계산대 동시 운영

---

## 2. 왜 「판매」를 재고 차감과 따로 두는가

재고를 그냥 −1 하면 **판매인지 파손인지 오조작인지 구분이 사라진다.**
이미 만들어 둔 `inventory_moves` 원장은 그 구분을 `reason` 으로 들고 있다.
판매는 여기에 `'sale'` 로 들어오고, **판매 문서(sale)** 가 그 근거가 된다.

```
sale (판매 1건)
 └ sale_items (품목들)
      └ inventory_moves (reason='sale', 품목마다 1행)
```

되짚는 방향도 성립한다 — 원장 한 줄에서 어느 판매인지 찾아갈 수 있어야 한다.

## 3. 데이터 모델 (제안)

```sql
-- 판매 1건
create table public.sales (
  id            bigserial   primary key,
  user_id       uuid        not null references auth.users(id) on delete cascade,
  -- 사람이 부르는 번호. 날짜 기준 일련번호(예: 20260905-014)
  sale_no       text        not null,
  status        text        not null default 'paid',   -- 'paid' | 'void' | 'refunded' | 'partial_refunded'
  -- 금액은 확정 시점의 값을 **복사해 둔다**. 나중에 정가가 바뀌어도 영수 내역은 안 바뀐다.
  subtotal      int         not null,   -- 품목 합계(할인 전)
  discount      int         not null default 0,
  total         int         not null,   -- 실제 받은 금액
  pay_method    text        not null,   -- 'cash' | 'card' | 'transfer' | 'other'
  memo          text,
  sold_at       timestamptz not null default now(),
  voided_at     timestamptz,
  unique (user_id, sale_no)
);

-- 판매 품목
create table public.sale_items (
  id            bigserial primary key,
  user_id       uuid      not null references auth.users(id) on delete cascade,
  sale_id       bigint    not null references public.sales(id) on delete cascade,
  book_id       bigint    not null references public.books(id) on delete restrict,
  -- 확정 시점 복사본. books 의 제목·가격이 나중에 바뀌어도 영수 내역은 그대로다.
  isbn          text      not null,
  title         text,
  unit_price    int       not null,
  quantity      int       not null check (quantity > 0),
  discount      int       not null default 0,
  line_total    int       not null,
  -- 반품된 수량. 부분 반품을 위해 품목 단위로 센다.
  refunded_qty  int       not null default 0 check (refunded_qty >= 0)
);
```

**결정 사항 세 가지와 그 이유**

| 결정 | 왜 |
|---|---|
| 금액·제목을 품목에 **복사**한다 | 영수 내역은 그때의 사실이다. 원본이 바뀌어도 따라 바뀌면 안 된다 |
| `book_id` 는 `on delete restrict` | 판매 기록이 있는 도서를 지울 수 없어야 한다. cascade 로 두면 매출이 사라진다 |
| 상태에 `partial_refunded` 를 둔다 | 부분 반품을 「전부 아니면 전무」로 뭉개면 남은 수량을 표현할 곳이 없다 |

### 되짚기 연결

`inventory_moves` 에 판매를 가리키는 열을 더한다(덧붙이기 마이그레이션).

```sql
alter table public.inventory_moves
  add column if not exists sale_id bigint references public.sales(id) on delete set null;
```

`on delete set null` 인 이유 — 판매가 지워져도 **재고가 움직였다는 사실은 남아야 한다.**

## 4. 판매 확정 절차 (RPC 하나로)

`checkout(p_items jsonb, p_pay_method text, p_discount int, p_memo text)`

한 트랜잭션 안에서 순서대로 한다. **중간에 끊기면 전부 없던 일이 되어야 한다** —
재고만 줄고 판매가 안 남거나 그 반대가 되면 장부가 맞지 않는다.

1. 품목별로 재고가 **충분한지 먼저 전부 확인**한다
   - 하나라도 모자라면 `raise exception` 으로 통째로 되돌린다
   - ⚠️ 하나씩 차감하며 진행하면 중간에 실패했을 때 앞의 것만 빠진다
2. `sales` 1행 + `sale_items` N행 삽입
3. 품목마다 `inventory` 차감 + `inventory_moves` 에 `reason='sale', sale_id=…` 기록
4. 확정된 `sales` 행을 돌려준다

### 재고가 모자랄 때

**기본은 막는다.** 다만 실무에서는 「장부보다 실물이 더 있는」 경우가 흔하다.
그래서 `p_allow_negative` 를 두되 **기본값은 거짓**으로 하고, 넘겼을 때는
`inventory_moves.memo` 에 「재고 부족 상태로 판매」를 남긴다.
조용히 음수를 허용하면 재고 숫자를 아무도 믿지 않게 된다.

### 취소와 반품

- **취소(void)** — 당일 오조작. 판매 전체를 무효로 하고 재고를 되돌린다.
  `reason='sale_void'` 로 원장에 **되돌리는 행을 새로 쌓는다.** 기존 행을 지우지 않는다.
- **반품(refund)** — 품목·수량 단위. `sale_items.refunded_qty` 를 올리고
  그만큼 재고를 되돌린다(`reason='sale_refund'`).
- 둘 다 원본 판매를 수정하지 않는다. **덧붙이기만 한다.**

## 5. 화면

### 5.1 판매 화면 (새 탭 「판매」)

```
┌ 상단 ─────────────────────────────┐
│ 판매  20260905-014     [스캔 켜기] │
├ 장바구니 ─────────────────────────┤
│ 고요한 아침의…   18,000  − 2 +  36,000 │
│ 자료구조         32,000  − 1 +  32,000 │
│ …                                      │
├ 합계 ─────────────────────────────┤
│ 소계        68,000                     │
│ 할인      [   0    ]                   │
│ 받을 금액   68,000                     │
├ 결제 ─────────────────────────────┤
│ [현금] [카드] [이체] [기타]            │
│        [ 판매 확정 ]                   │
└────────────────────────────────────┘
```

- 스캔을 켜두면 **찍는 대로 장바구니에 쌓인다.** 같은 책을 다시 찍으면 수량이 는다.
  (도서 담기의 「보이는 동안 1회」 규칙과 **다르다** — 여기서는 찍는 만큼 세는 것이 맞다.
  그래서 판매 화면은 그 게이트를 끄고 쓴다. §7 참조)
- 재고가 모자란 품목은 줄에 표시하고, 확정 버튼 옆에 사유를 적는다.

### 5.2 판매 내역

- 일자별 목록: 번호·시각·품목 수·금액·결제 수단·상태
- 한 건을 열면 품목과 취소·반품 버튼
- 상단에 그날 합계(건수·매출·결제 수단별)

### 5.3 엑셀

시트 3장을 더한다. 기존 파일 구조를 그대로 따른다(요약이 맨 앞).

| 시트 | 내용 |
|---|---|
| `판매` | 판매 1건이 1행. 번호·시각·금액·결제수단·상태 |
| `판매품목` | 품목이 1행. 판매번호·ISBN·제목·단가·수량·금액·반품수량 |
| `일자별매출` | 날짜별 건수·매출·결제 수단별 합계 |

요약 시트에 「기간 매출」 절을 더한다. **합계에는 항상 분모를 적는다**(몇 건 기준인지).

## 6. 만들 때 지킬 것

- **금액은 정수(원)로만 다룬다.** 부동소수를 쓰면 합계가 1원씩 어긋난다.
- **할인은 금액으로 저장한다.** 비율로 저장하면 재계산할 때마다 반올림이 달라진다.
  화면에서 비율로 입력받되 저장은 계산된 금액으로 한다.
- **판매번호는 DB 가 만든다.** 클라이언트가 만들면 같은 번호가 두 번 나온다.
- **확정 버튼은 멱등해야 한다.** 두 번 눌리거나 네트워크가 끊겨 재시도될 때
  판매가 두 건 생기면 안 된다 → 클라이언트가 만든 `idempotency_key` 를 `sales` 에 유니크로.
- **재고 검사와 차감은 같은 트랜잭션에서.** 검사 후 차감 사이에 다른 판매가 끼면 음수가 된다.
- 상태 전이에 **막다른 상태를 두지 않는다.** `void`·`refunded` 각각에서 다음에 할 수 있는
  행동이 화면에 보여야 한다.

## 7. 착수 전에 답이 필요한 것

이 답에 따라 데이터 모델이 달라진다. **추측으로 채우지 않는다.**

1. **판매 단가의 기준은 무엇인가.**
   정가인가, 중고가인가, 매번 손으로 넣는가? 중고 서적이면 책마다 다를 텐데
   그렇다면 단가는 재고(`inventory`)에 붙어야 한다 — 지금은 없는 열이다.
2. **재고가 없는 책도 팔 수 있어야 하는가.**
   된다면 판매가 재고를 음수로 만들 수 있고, 안 된다면 판매 전에 재고 등록이 강제된다.
3. **부가세를 다루는가.** 다룬다면 품목별 과세 여부와 세액 열이 필요하다.
4. **영수증을 출력하는가.** 출력한다면 프린터 규격(감열 58/80mm)과 연결 방식이 먼저다.
5. **판매 화면에서 스캔은 「찍는 만큼」인가.**
   도서 담기는 「보이는 동안 1회」다. 판매는 반대여야 자연스러운데, 두 규칙이
   한 앱에 공존하면 사용자가 헷갈린다. 화면마다 다르다는 것을 어떻게 알릴지 정해야 한다.
6. **여러 사람이 동시에 파는가.** 그렇다면 판매번호 채번과 재고 차감에 잠금이 필요하다.

## 8. 대략의 크기

| 덩어리 | 내용 |
|---|---|
| 데이터 | 마이그레이션 2개(sales·sale_items, moves 열 추가), RPC 3개(checkout·void·refund) |
| API | `/api/sales` CRUD, `/api/sales/[id]/void`, `/api/sales/[id]/refund` |
| 화면 | 판매 탭(장바구니·결제), 판매 내역 탭, 스캔 연동 |
| 엑셀 | 시트 3장 + 요약 절 |
| 검증 | 금액 계산·재고 검사·멱등성 단위 시험, 확정→취소→반품 풀체인 시험 |

§7 이 정리되기 전에는 기간을 산정하지 않는다 — 1번 답 하나로 재고 모델이 바뀐다.
