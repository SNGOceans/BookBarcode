## 2. 작업 축별

### 2.1 판독 엔진 사다리 — 가장 큰 개선

`lib/scanner/engines.ts`

- 엔진 셋을 성능 순으로 세우고 앞이 놓치면 뒤가 받는다.
  1. **내장 `BarcodeDetector`** — 안드로이드 크롬에 들어 있는 구글 엔진. 영상을 그대로 넘길 수 있어 픽셀 복사가 0.
  2. **zxing-wasm** — `tryHarder`·`tryRotate`·`tryInvert`. iOS 사파리에는 내장 엔진이 없어 여기가 1순위가 된다.
  3. **zbar-wasm** — 기존 엔진. 반듯하고 선명한 바코드에 여전히 빠르다.

- **왜 사다리인가 (측정 근거).** 어느 엔진도 혼자 이기지 못했다.
  안드로이드 크롬 실기기 측정(합성 32케이스, `/scan-lab`):

  | 엔진 | 인식 |
  |---|---|
  | 내장 BarcodeDetector | 24/32 |
  | zbar | 17/32 |
  | zxing | 16/32 |

  Node 벤치(합성 32케이스, 2560×1440)에서는 zxing 단독이 24/32 로 **개편 전(25/32)보다 낮았지만**,
  기울고 흐린 18% 거리 케이스를 유일하게 잡았고 반대로 대각+악조건 3건은 zbar 만 잡았다.
  둘을 이어 붙이면 27/32 로 각각을 넘는다. → 단일 엔진 교체가 아니라 위임 구조가 정답이다.

- **함정 1.** 내장 엔진은 안드로이드에서 Play 서비스 모듈이 있어야 실제로 동작한다.
  모듈이 없으면 **생성자는 멀쩡한데 `getSupportedFormats()` 가 비고 `detect` 가 늘 빈 배열**을 준다.
  「조용히 아무것도 못 읽는 엔진」이 사다리 맨 앞에 서는 것이 가장 나쁘므로
  `ean_13` 지원이 목록에 **명시적으로** 있을 때만 채택한다(`engines.ts` 의 `createNativeEngine`).

- **함정 2.** wasm 을 미리 다 받으면 안드로이드는 쓰지도 않을 1.6MB 를 내려받는다.
  엔진 자리(`EngineSlot`)만 먼저 세우고 순환이 그 자리에 처음 닿을 때 로드한다.

- **함정 3.** `zxing-wasm` 은 자기 스크립트 옆에서 wasm 을 찾는데 번들링하면 그 경로가 사라진다.
  `scripts/copy-wasm.mjs` 가 `prebuild`/`predev` 에서 `public/` 으로 복사한다.
  손으로 한 번 복사해 두면 다음 업그레이드에 조용히 어긋나고, **그 고장은 로컬이 아니라 배포본에서만** 난다.

### 2.2 전처리 전략 사다리

`lib/scanner/pipeline.ts` · `lib/scanner/frame.ts`

- 전략 7종을 틱마다 하나씩 돌리고 **성공한 전략은 고정**한다(빠른 경로). 연속으로 놓치면 다시 탐색.
- 전략 = 크롭 비율 × 목표 폭(업샘플/다운샘플) × 명암 스트레치 × 언샤프 × 회전각.
- **45도 회전 판을 넣은 이유** — zbar 는 가로·세로 스캔라인만 쓴다. 0°와 90° 부근은 잘 읽고
  그 사이(대략 25°~65°)가 사각지대다. 45° 판 한 장이면 그 구간이 0° 부근으로 옮겨와 덮인다.
  **−45° 는 넣지 않았다.** 가로·세로를 모두 보는 한 두 대각선이 +45° 한 장으로 같이 덮인다.
- **함정.** 회전하면 모서리에 빈 곳이 생긴다. **흰색으로 채워야 한다** — 검은 여백은 굵은 바로 오인된다.
  그리고 그 흰 여백이 명암 분포를 밝은 쪽으로 끌어당겨 보정이 꺼져버리므로,
  회전 전략에서는 **여백이 닿지 않는 중앙 정사각형만 표본**으로 삼는다(`buildStretchLut` 의 `sample` 인자).

### 2.3 인식 실시간 표시 (`df29398` 에서 형태 변경)

`components/Scanner.tsx`

- **최종 형태** — 붉은 기준선이 화면 세로 중앙을 가로지르고, 인식 지점을 **그 선 위에 x 위치로만 점**으로 찍는다.
  바코드를 감싸는 사각형은 두지 않는다.
- 기준선과 점을 **같은 캔버스에서 함께 그린다.** 선을 CSS 로 따로 두면(애니메이션이면 더욱)
  점과 위치가 어긋난다. 그래서 `.scan-line`·`.scan-frame` CSS 를 제거했다.
- 화면 좌표와 영상 좌표가 1:1 로 맞아야 점이 제자리에 찍히므로,
  컨테이너 `aspect-ratio` 를 **실제 촬영 비율로 런타임에 맞춘다**(`object-fit: contain`).
  기존에는 4/3 컨테이너에 `cover` 라 좌우가 잘려 보이고 있었다.
- 첫 구현은 사각형 외곽선 + 꼭짓점 고리였는데 사용자가 「점만 찍는 형태」를 지정해 바꿨다.

### 2.3.1 한 번에 하나만 기록 (`df29398`)

한 프레임에 여러 바코드가 잡혀도 **사용자가 겨눈 것은 하나**다.
검출들을 기준선(세로 중앙)에서의 거리로 정렬해 **가장 가까운 하나만** 기록한다.
나머지는 `scan.multi` 로그로만 남긴다. zxing 도 `maxNumberOfSymbols` 를 1 로 낮춰
엔진 단계에서부터 일을 줄인다.

### 2.4 중복 기록 방지

`lib/scanner/pipeline.ts` 의 `PresenceGate`

- 규칙은 **「보이는 동안 1회」**다. 코드가 1.5초 동안 한 번도 안 잡히면 사라진 것으로 보고,

### 2.5 엑셀

`app/api/export/xlsx/route.ts` · `lib/book-meta.ts`

- 열 순서: 제목 · ISBN · 정가 · 중고가 · 중고최저가 · 중고수량 · 판매가 · 저자 · 옮긴이 · 출판사 · 스캔횟수 · 최초/최근 스캔

- **탭 3개로 나눴다**: `요약` · `검색됨` · `검색 안 됨`. 요약을 맨 앞에 둬서
  파일을 열면 전체 그림이 먼저 보이게 했다.
- **조회 상태는 3값이다** — 「찾음 / 못 찾음 / 미조회」.
  「못 찾음」(알라딘에 자료 없음)과 「미조회」(우리가 아직 안 물어봄)는 대응이 정반대다.
  앞은 사람이 손으로 채워야 하고 뒤는 조회를 한 번 더 돌리면 된다. 뭉치면 그 구분이 사라진다.
  이 판정은 `lib/book-meta.ts` 로 빼서 시험을 붙였다 — 라우트 안에 있으면 시험할 수 없고,
  시험 못 하는 분류는 파일이 멀쩡히 만들어지면서 책만 엉뚱한 탭에 들어간다.
- **합계에는 분모를 함께 적는다.** 「정가 합계 · 12권 기준」처럼 몇 건이 기여했는지 쓴다.
  값이 없는 도서를 빼고 더한 숫자는 분모 없이는 오해를 부른다.

## 2.8 속도 회귀와 그 원인 (`df29398`)

개편 직후 사용자가 **「인식 속도가 느려졌다」**고 지적했다. 원인은 UI 하나가 아니라 둘이었다.

**원인 1 — 사다리를 끝까지 걸어 올라간다.**
놓치기 시작하면 점점 비싼 전략으로 올라가는데, 뒤쪽 전략은 큰 버퍼에 언샤프 3패스라
한 번에 100ms 를 넘는다. 적응형 간격까지 같이 늘어나 초당 시도가 급감한다.
그 사이 사용자가 바코드를 제대로 갖다 대도 **비싼 전략을 돌고 있느라 늦게 잡는다.**

→ 처방: 탐색 중에는 **가장 싼 조합 (0,0) 을 매번 사이에 끼운다**(`ScanCycle.probeTurn`).
흔한 경우는 항상 빠르게 잡히고, 어려운 경우는 그 사이사이에 계속 시도된다.

**원인 2 — 오버레이가 매 프레임 비싼 일을 했다.**
`getBoundingClientRect()`(레이아웃 강제)와 `createLinearGradient()`(객체 생성)를 프레임마다 부르고,
스캔이 끝날 때마다 React 상태를 갱신했다.

→ 처방: 크기·그라디언트를 캐시(0.5초에 한 번만 재확인), 상태는 **값이 실제로 바뀔 때만** 갱신,
표시용 수치는 0.5초에 한 번만. 스캔 간격 계수도 0.5→0.35, 상한 200→150ms 로 조였다.

**전략 폭을 줄일 때의 함정 — 대가가 균일하지 않다.**
속도를 위해 네 전략의 목표폭을 한꺼번에 줄였더니 인식이 27건 → 26건이 됐다.
어느 것이 범인인지 하나씩 되돌려 재 봤다.

| 변경 | 인식률 |
|---|---|
| `wide-45` 1440→1280 · `tele-45` 1700→1300 · `mid-sharp` 1800→1400 | 변화 없음 (공짜) |
| `tele-sharp` 2000→1500 | 27 → **26** (1건 손실) |
| `tele-sharp` 1800 | **27 회복** |

⇒ 멀고 흐린 케이스를 살리는 것은 **`tele-sharp` 의 폭 하나**였다. 거기만 지키고 나머지는 줄였다.
「속도를 위해 폭을 줄인다」를 뭉뚱그려 적용했으면 이유도 모른 채 인식률을 잃었을 것이다.

## 3. 함정 — 운영 DB 를 지울 뻔한 것 (가장 중요)

원격 Supabase 의 마이그레이션 이력이 **비어 있었다.** 지금까지 SQL 편집기로 직접 실행했다는 뜻이다.

이 상태에서 `supabase db push` 를 그냥 돌리면 **`0001_init.sql` 부터 실행된다.**
그 파일 첫 줄은 다음과 같다.

```sql
drop table if exists public.books cascade;
```

즉 운영 데이터(도서 11행 · 스캔 33행)가 지워진다.

**처방 — 이력만 맞추고 신규분만 올린다.**

```bash
supabase migration repair --status applied 0001 --linked   # SQL 을 실행하지 않고 이력만 기록
supabase db push --dry-run --linked                        # 무엇이 올라가는지 눈으로 확인
supabase db push --linked                                  # 0002 만 적용
```

적용 후 대조: `books` 11행 · `scans` 33행 **그대로**, `app_logs` 신설(0행).

> 다음 사람에게: 이 저장소에서 `db push` 를 처음 돌릴 때는 **반드시 `--dry-run` 을 먼저** 본다.
> 「무엇이 올라가나」를 확인하지 않은 push 는 이 저장소에서 파괴적이다.

**시험이 틀렸던 사례 1건.** 명암 보정 시험이 처음에 빨간불이었는데 제품이 아니라 **시험이 틀렸다.**
표본의 명암 폭을 12 미만으로 만들어 두고 「보정이 나와야 한다」고 단언했는데,
그 함수는 폭이 12 미만이면 잡음만 커지므로 일부러 보정하지 않는다. 시험을 고쳤다.

**측정할 수 없어 판정 불가로 둔 것.** 내장 `BarcodeDetector` 는 브라우저 API 라 Node 벤치로 잴 수 없다.
그래서 `/scan-lab` 페이지를 만들어 실기기에서 쟀다. 그 전까지는 이 경로의 인식률을 수치로 주장하지 않았다.

**한계 — 남은 실패 5건.** 전부 거리 12~18% 에 흐림·반사광이 겹친 경우다.
초점 흐림은 각도 기준이라 해상도를 올려도 정보가 같이 뭉개져 **픽셀을 늘려서 풀리지 않는다.**
실기기에서는 확대(zoom)·조명(torch)으로 푸는 것이 맞고, 두 제어를 화면에 노출해 두었다.

### 6.2 결정이 필요한 것

- **엑셀 「중고최고가」 열** — 알라딘 `usedList` 는 채널별 `minPrice`·`itemCount` 만 준다.
  최고가에 해당하는 값이 응답에 **없다.** 돈에 관한 숫자를 지어내지 않으려고 열을 빼 두었다.
  선택지 3안은 `docs/백로그.md` §2.
- **로그 보존 기간** — 지금은 자동 정리가 없다. `docs/백로그.md` §3.

### 6.3 아직 확인 못 한 것

- **로그인 뒤 화면(사이드바·로그 탭)의 실제 동작**은 눈으로 못 봤다.
  로컬에 Supabase 자격증명이 없어 로그인을 할 수 없었고, 스타일시트만 실제 브라우저에서 검증했다.

- **iOS 실기기 측정.** 에뮬레이터는 안드로이드만 있었다. iOS 는 내장 엔진이 없어
  가장 약한 경로로 도는데, 그 경로의 실제 인식률을 아직 재지 못했다.
